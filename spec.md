# Завдання 3. Sequence-діаграми для бібліотеки

**Предметна область:** бібліотечний каталог і облік видач паперових примірників.

Цей документ продовжує [Завдання 1 — ER бібліотеки](https://github.com/Alex9011/Lab1_KPI2/blob/master/spec.md) і Завдання 2. Діаграми нижче показують очікувану поведінку системи; готового серверного коду в цій роботі немає.

## 1. Що описуємо

Фокус роботи — оформлення видачі фізичного примірника (`UC-05`). Показано, як бібліотекар взаємодіє із системою у восьми сценаріях із Завдання 2: від звичайної видачі до помилок і двох одночасних запитів. Для кожного сценарію є Mermaid-вихідник, SVG і PNG.

Діаграми мають відповідати сценаріям Gherkin і не суперечити ER-моделі з першої лабораторної. У них показані виклики, відповіді, активації та відповідні комбіновані фрагменти (`alt`, `opt` або `par`). Файли SVG і PNG генеруються з `.mmd`, а три найважливіші ризики описані в аудиті нижче та в `DEFENSE.md`.

## 2. Обраний прецедент

**UC-05 «Оформити видачу примірника».** Ініціатор — **Бібліотекар**. Мета — оформити одну видачу конкретного `Copy` конкретному `Member` до заданої дати `due_at`. Видача створює **нову** `Loan` з окремим `loan_id`, `borrowed_at` (серверний час UTC), `due_at > borrowed_at`, `returned_at = NULL`; завершені історичні `Loan` не змінюються.

**Для успішної видачі** бібліотекарю потрібні чинні права, а `Member` і `Copy` мають існувати. У примірника не повинно бути відкритої `Loan`. Якщо будь-яка перевірка не проходить, нова `Loan` не створюється. При двох одночасних запитах на один `Copy` успішним може бути лише один. Помилки перевіряються в такому порядку: роль → Member → Copy → час → доступність.

**Зв'язки з іншими UC:** з ЛР2 збережено включення `UC-03 «Знайти читача»` та `UC-02 «Переглянути доступність примірника»` до `UC-05`. Умовний `UC-06 «Повторно видати примірник»` розглядається як варіація `UC-05`, а не новий основний сценарій.

У цій роботі не розглядаються каталогізація `Book`/`Author`, реєстрація `Member`, повернення, бронювання, штрафи, філії та адміністрування облікових записів. Діаграми також не є готовим дизайном БД чи production API.

## 3. Сценарії з Завдання 2

### 3.1. Ідентифікатори, передумови та результат

| Сценарій | Вхідна умова | Очікуваний результат |
|---|---|---|
| S-01 | Дійсні Member M1, Copy C1 без відкритої Loan | Створити L1 з новим UUID, показати due_at |
| S-02 | Є завершена L0 для M1 і C1, нових відкритих Loan немає | Створити L1; L0 зберегти незмінною |
| S-03 | Відкрита Loan L0 уже пов'язана з C1 | Відмова «Примірник уже видано»; нуль записів |
| S-04 | due_at дорівнює або передує часу видачі | Одна й та сама помилка строку; нуль записів |
| S-05 | Member M404 відсутній | «Читача не знайдено»; Copy не перевіряється після відмови |
| S-06 | Member M1 є, Copy C404 відсутній | «Примірник не знайдено»; Loan не створюється |
| S-07 | B1 і B2 одночасно запитують C1 для M1/M2 | Рівно один успіх, один конфлікт; 1 відкрита Loan |
| S-08 | Немає сесії або ролі бібліотекаря | «Недостатньо прав»; не звертатися до LoanService / LibraryDB |

### 3.2. Сценарії Gherkin

**S-01. Успішна перша видача**

```gherkin
Scenario: Видача доступного примірника читачеві
  Given бібліотекар має активну авторизовану сесію
  And існує читач Member M1
  And існує примірник Copy C1 без відкритої видачі
  And поточний час сервера 2026-11-01T10:00:00Z
  When бібліотекар оформлює видачу C1 для M1 до 2026-11-15T10:00:00Z
  Then створюється рівно одна нова Loan з унікальним loan_id
  And member_id = M1 та copy_id = C1
  And borrowed_at = 2026-11-01T10:00:00Z
  And due_at = 2026-11-15T10:00:00Z, returned_at = NULL
  And бібліотекар бачить підтвердження з номером видачі та строком повернення
```

**S-02. Повторна видача того самого примірника**

```gherkin
Scenario: Повторна видача після повернення
  Given бібліотекар має активну авторизовану сесію
  And існують Member M1 та Copy C1
  And попередня Loan L0 для M1 та C1 має returned_at = 2026-10-20T12:00:00Z
  And інших відкритих Loan для C1 немає
  And поточний час сервера 2026-11-01T10:00:00Z
  When бібліотекар оформлює видачу C1 для M1 до 2026-11-08T10:00:00Z
  Then створюється нова Loan L1 з loan_id, відмінним від L0
  And дані попередньої Loan L0 не змінюються
  And нова Loan має returned_at = NULL
  And бібліотекар бачить підтвердження з loan_id та due_at
```

**S-03. Примірник уже виданий**

```gherkin
Scenario: Відмова, якщо примірник має відкриту видачу
  Given бібліотекар має активну авторизовану сесію
  And існують Member M1 та Copy C1
  And для C1 існує Loan L0 з returned_at = NULL
  When бібліотекар оформлює видачу C1 для M1 до 2026-11-15T10:00:00Z
  Then система відмовляє з причиною "Примірник уже видано"
  And нова Loan не створюється, а L0 залишається без змін
```

**S-04. Неприпустимий строк повернення**

```gherkin
Scenario Outline: Відмова, якщо строк не пізніше видачі
  Given бібліотекар має активну авторизовану сесію
  And існують Member M1 та доступний Copy C1
  And поточний час сервера 2026-11-01T10:00:00Z
  When бібліотекар оформлює видачу C1 для M1 до <строк>
  Then система відмовляє з причиною "Строк має бути пізніше часу видачі"
  And нова Loan не створюється
  Examples:
    | строк                |
    | 2026-11-01T10:00:00Z |
    | 2026-10-31T10:00:00Z |
```

**S-05. Читача немає в каталозі**

```gherkin
Scenario: Відмова для неіснуючого читача
  Given бібліотекар має активну авторизовану сесію
  And Member M404 не існує
  And Copy C1 існує й доступний
  When бібліотекар оформлює видачу C1 для M404 до 2026-11-15T10:00:00Z
  Then система відмовляє з причиною "Читача не знайдено"
  And нова Loan не створюється
```

**S-06. Примірника немає в каталозі**

```gherkin
Scenario: Відмова для неіснуючого примірника
  Given бібліотекар має активну авторизовану сесію
  And Member M1 існує
  And Copy C404 не існує
  When бібліотекар оформлює видачу C404 для M1 до 2026-11-15T10:00:00Z
  Then система відмовляє з причиною "Примірник не знайдено"
  And нова Loan не створюється
```

**S-07. Дві одночасні заявки на один примірник**

```gherkin
Scenario: Лише одна видача під час паралельних запитів
  Given бібліотекарі B1 та B2 мають активні авторизовані сесії
  And існують Member M1, Member M2 та доступний Copy C1
  And обидва запити надходять одночасно для C1 з допустимим due_at
  When B1 оформлює видачу C1 для M1, а B2 оформлює видачу C1 для M2
  Then один запит завершується успіхом, а інший — відмовою "Примірник уже видано"
  And серед Loan для C1 існує рівно одна відкрита видача
  And не виникає частково створених записів
```

**S-08. Неавторизована спроба**

```gherkin
Scenario: Відмова без сесії бібліотекаря
  Given сесія користувача відсутня або не має ролі бібліотекаря
  And Member M1 та доступний Copy C1 існують
  When користувач надсилає запит на видачу C1 для M1
  Then система відмовляє з повідомленням "Недостатньо прав"
  And нова Loan не створюється
```

`M1`, `C1`, `L0` — тестові псевдоніми для реальних UUID; це не додаткові атрибути ER-моделі. Час у тестових прикладах фіксується тестовим годинником; у робочій системі це UTC-час сервера.


## 4. Учасники взаємодії

| Позначення | Роль у sequence | Зіставлення з ЛР1 |
|---|---|---|
| Бібліотекар / Бібліотекар B1, B2 | Зовнішній бізнес-актор, ініціює оформлення видачі | Актор ЛР2; **не** таблиця ER |
| Форма видачі | Збирає `member_id`, `copy_id`, `due_at`; показує результат | UI-компонент, не доменна сутність |
| `LoanController` | Приймає `submitLoan()`, перевіряє права і передає запит | Приклад прикладного компонента |
| `AccessGuard` | Перевіряє сесію і роль працівника | Технічний компонент, не `Member` і не ER-сутність |
| `LoanService` | Реалізує правила видачі, дату та транзакційність | Оперує `Member`, `Copy`, `Loan` |
| `LibraryDB` | Читає `Member`/`Copy` і зберігає `Loan`; блокує `Copy` в транзакції | Сховище п'яти сутностей ЛР1; у UC-05 задіяні три |

`LoanController`, `LoanService`, `AccessGuard` і `LibraryDB` потрібні тут, щоб було зрозуміло, між якими частинами системи проходить запит. Це не нові таблиці ER-моделі. `Book` і `Author` у сценаріях видачі безпосередньо не використовуються.

**Дані:** `M1`, `C1`, `C404`, `L0`, `L1` — тестові імена UUID, а не текстові PK. Система не зберігає `Copy.available`: доступність обчислює як **відсутність `Loan` з даним `copy_id` і `returned_at IS NULL`**. Усі дати `Loan` — UTC, повторні видачі мають окремі `loan_id`.

## 5. Детальні кроки взаємодії

Джерело і рендер кожного сценарію наведено в §6. У діаграмах `->>` означає виклик, а `-->>` — відповідь. `activate`/`deactivate` показують, поки компонент обробляє запит; на гілках `alt` активація триває до завершення відповідної операції.

**S-01 — успішна перша видача.** Бібліотекар передає через форму M1, C1 і `due_at`. Контролер перевіряє права, після чого сервіс знаходить Member і Copy та перевіряє дату. У транзакції Copy блокується, перевіряється відсутність відкритої Loan, створюється L1 і виконується commit. У відповідь бібліотекар отримує `loan_id` і `due_at`. `alt` показує перевірку дати.

**S-02 — повторна видача.** Після авторизації система знаходить Member і Copy та перевіряє строк. Під блокуванням C1 відкритої Loan немає, але завершена L0 залишається в історії. `opt` підкреслює, що L0 не змінюється. Далі створюється нова L1 з іншим UUID, виконується commit і повертається підтвердження.

**S-03 — примірник уже виданий.** Після перевірки прав, Member, Copy і строку система під блокуванням C1 знаходить L0 з `returned_at=NULL`. Гілка `alt` завершує транзакцію без створення запису та повертає повідомлення про конфлікт. L0 залишається без змін.

**S-04 — неправильний `due_at`.** Після авторизації та пошуку Member і Copy сервер визначає `borrowed_at`. Дві гілки `alt` відповідають прикладам Gherkin: строк дорівнює часу видачі або є ранішим. В обох випадках повертається однакове повідомлення, а `insertLoan()` не викликається.

**S-05 — Member відсутній.** Після авторизації `findMember(M404)` повертає `null`. Фрагмент `opt` завершується помилкою `MemberNotFound` і повідомленням для бібліотекаря. Copy після цього не шукається, Loan не зберігається.

**S-06 — Copy відсутній.** Після авторизації система знаходить M1, але `findCopy(C404)` повертає `null`. Фрагмент `opt` завершується помилкою `CopyNotFound`; Loan не створюється.

**S-07 — два конкурентні запити.** Два бібліотекарі B1 і B2 одночасно надсилають запити на один C1, що показано фрагментом `par`. Кожна транзакція бере ексклюзивне блокування цього Copy і після цього ще раз перевіряє відкриту Loan. Той, хто першим отримає блокування, створює запис; другий побачить його й отримає конфлікт. Хто саме переможе, діаграма не визначає — це залежить від порядку блокування.

**S-08 — немає прав.** Користувач надсилає запит, а `AccessGuard` у двох гілках `alt` перевіряє відсутність сесії або ролі. Контролер повертає «Недостатньо прав». До `LoanService` і `LibraryDB` запит не доходить, тому жодна Loan не змінюється.

## 7. Аудит: spec ↔ Gherkin ↔ sequence ↔ ER

| № | Розбіжність / ризик | Коригування в sequence | Перевірка |
|---|---|---|---|
| **A1** | Можна помилково показати `Copy.available` як збережене поле, хоча його немає в ЛР1. | В S-01/S-03/S-07 виконано `findOpenLoan(C1)` за `returned_at=NULL`; поле `available` не введено. | Звірка з ER ЛР1 (Copy має `copy_id`, `inventory_number`, `book_id`). |
| **A2** | Під час повторної видачі можна помилково перезаписати L0 або вважати `(member_id, copy_id)` унікальним ключем. | S-02 зберігає завершену L0 та створює окрему L1 з новим `loan_id`. | Порівняння з правилом повторних видач C2 ЛР1 і Gherkin S-02. |
| **A3** | Роздільні `findOpenLoan()` та `insertLoan()` без синхронізації дають подвійну видачу під час конкурентних запитів. | S-07 показує `par`, блокування одного C1 до перевірки та атомарне завершення транзакції. | Для двох одночасних запитів допускається лише один успіх; інший отримує 409. |

Ці три пункти — місця, де під час проєктування легко помилитися. Вони не описують проблеми вже реалізованого коду: у цій роботі розглядаються саме моделі взаємодії.

### 7.1. Перевірка зв'язків

- **ER ЛР1:** `Member (1) → Loan (0..*)`, `Copy (1) → Loan (0..*)`; одна Loan належить одному Member і одному Copy. Кожна нова видача — новий UUID `loan_id`; історичні інтервали не перетинаються.
- **ЛР2:** 8 сценаріїв із `UC-05`, контроль прав, Member/Copy, строку, доступності, повтору й конкурентності. Ці сценарії **не змінено** в §3.2.
- **Завдання 3:** для кожного S-01…S-08 є зв'язана діаграма; кроки та відповіді з §5 відображають Then у Gherkin.
- **Технічні учасники:** роль не є новою сутністю ER. `AccessGuard`, `Controller`, `Service` і `LibraryDB` лише розділяють логіку між учасниками діаграми.
- **Activation bars:** для компонентів, що працюють усередині `alt`/`opt`, `activate` стоїть перед фрагментом, а `deactivate` — після нього. У `par` кожна паралельна обробка має власну активацію.

### 7.2. Невирішені деталі реалізації

Тип БД, спосіб перевірки ролі, вид блокування, ізоляція транзакції, HTTP-коди та конкретні класи компонентів тут не фіксуються. Це рішення для майбутньої реалізації, які треба буде узгодити окремо. Коди `404/409/422/403` у sequence наведені лише як зручний умовний контракт для тестів.
