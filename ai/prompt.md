Перевір доцільність такого розподілу, визнач послідовність синхронних викликів і return-повідомлень та запропонуй комбіновані фрагменти UML для сценаріїв S-01–S-08.

Важливо не змінювати бізнес-правила попередніх лабораторних, зокрема принцип збереження історії Loan і визначення доступності примірника через returned_at = NULL.

Промпт 3. Уточнення аудиту та трьох ключових розбіжностей

Хочу уточнити розділ Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення.

Оскільки це третя лабораторна, аудит має стосуватися саме Sequence-діаграм, а не повторювати проблеми ER-моделі чи Use Case з попередніх робіт.

Проаналізуй три найбільш суттєві невідповідності у взаємодії компонентів: неправильну обробку альтернативних сценаріїв, продовження виконання після помилки та конкурентне оформлення видач.

Для кожного випадку перевір, чи справді проблема була присутня у попередній версії файлу, і зістав її з історією Git.

Мені потрібен аудит, у якому кожне виправлення можна підтвердити конкретним diff та SHA коміту. Якщо історія не підтверджує певне твердження, його потрібно виключити або позначити як потенційний ризик.

Промпт 4. Підготовка Pull Request

Лабораторна зберігається в GitHub, основна робоча гілка — master.

Мені потрібно оформити Pull Request для перевірки результатів, не змінюючи існуючу історію комітів.

Запропонуй безпечний Git workflow із базовою гілкою, який дозволить показати реальні зміни проєкту та їх послідовність.

Поясни, як правильно вибрати base і compare, як перевірити diff перед створенням PR та як уникнути випадкового перезапису історії через force push.

Промпт 5. Структурування документа DEFENSE

Мені потрібно підготувати документ DEFENSE.md за визначеним шаблоном захисту ЛР3.

Допоможи структурувати такі частини:

Намір роботи та критерії правильності.

Три ключові розбіжності між специфікацією і Sequence-діаграмами.

Архітектурне рішення (ADR) з аналізом альтернатив.

Перевірка узгодженості з ER-моделлю та Gherkin-сценаріями.

У блоці ADR хочу обґрунтувати транзакційне блокування Copy перед повторною перевіркою findOpenLoan().

Порівняй цей підхід із використанням окремого поля Copy.available та перевіркою доступності без блокування. Особливу увагу приділи ризику race condition.

Використовуй лише підтверджені зміни й реальні коміти.

Промпт 8. Аналіз незарахованої перевірки AI-CHECK

Отримав негативний результат автоматичної перевірки ЛР3.

Основне зауваження стосується недостовірності попереднього аудиту: історія Git показує, що деякі проміжні коміти лише повертали файли до початкового стану.

Також виявлено проблеми з комбінованими фрагментами Sequence-діаграм:

S-05/S-06 — використання opt замість дострокового завершення;

S-04 — дві альтернативні гілки з ідентичним результатом;

S-01 — дублювання помилкового сценарію S-04.

Проаналізуй ці зауваження з позиції семантики UML і підготуй послідовний план виправлень.

Важливо виконати реальні зміни в діаграмах, перевірити їх за допомогою офіційного Mermaid CLI та зберегти прозору історію комітів без переписування попередніх версій.

Промпт 9. Технічне завдання для Codex

Підготуй технічне завдання для Codex на основі виявлених проблем.

Пріоритетом є семантична коректність Sequence-діаграм, а не формальне проходження перевірки.

Потрібно:

виправити обробку помилок у S-05/S-06;

спростити умову перевірки строку у S-04;

усунути дублювання альтернативи в S-01;

перевірити транзакційну логіку S-07;

виконати рендеринг офіційним Mermaid CLI;

забезпечити відповідність Gherkin та ER;

зафіксувати кожне реальне виправлення окремим осмисленим комітом.

Окремо зазнач, що історію Git не можна переписувати, а перевірки повинні мати відтворюваний результат.

Промпт 10. Аналіз частково виконаної роботи Codex

Codex повідомив про три локальні коміти, але не зміг завершити встановлення Mermaid CLI через ENOSPC.

Потрібно визначити, які етапи вже виконані, а які залишилися неперевіреними.

Запропонуй безпечне усунення проблеми з дисковим простором, перевірку стану Git та продовження роботи без втрати локальних комітів.

Окремо проаналізуй, чи правильно використані нові фрагменти break і critical та чи відповідають вони вимогам лабораторної.

До завершення перевірок не слід вважати роботу готовою.

Промпт 11. Завершальна перевірка та підготовка до здачі

Потрібно довести ЛР3 до повністю узгодженого стану.

Перевір усі актуальні Mermaid-діаграми, відтворюваність рендерингу, результати ai/check.py, коректність аудиту, ADR та документації.

Синхронізуй spec.md, DEFENSE.md, README й історію технічних виправлень із фактичним станом проєкту.

Не змінюй сценарії ЛР2 та сутності ЛР1.

Після завершення підготуй підсумковий звіт із переліком змінених файлів, результатами перевірок, справжніми SHA комітів та станом Pull Request №1.

Мета — не просто отримати позитивну оцінку автоматичної перевірки, а забезпечити логічну цілісність моделі взаємодії та можливість обґрунтувати кожне архітектурне рішення.
